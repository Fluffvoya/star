# ADR-0018：实施基线补充

- 状态：已确认
- 日期：2026-11-19
- 关联：[Star Engine 实现方案](../architecture/implementation-plan.md)；补充 ADR-0001、0003、0006、0009、0017。

## 背景

Star Engine 目前由一人维护，允许大量使用 AI 辅助开发。原方案存在三处需要收敛的边界：不同构建形态的 CMake 配置、游戏模块对底层 ECS 的依赖，以及热重载失败时编辑数据的归属。

## 决定

1. **平台与后端。** Windows x64、Linux x64、macOS arm64 都是正式支持目标；Apple Silicon 实机必验，Intel Mac 尽力支持。D3D11 是 Windows 1.0 的兼容后端，验证 Basic 路径和自动回退。不以降低正式平台支持来替代本地验证。
2. **构建。** 引擎、工具和游戏使用 CMake + Ninja；不维护 MSBuild 或 Xcode 构建链路。开发动态库与 Profile/Shipping 静态单体模式各自配置构建目录。IDE、编译器归属和平台 SDK 不改变构建器的统一选择。
3. **工程规范。** LLVM 格式为基线，缩进和 Tab 宽度均为 4，以空格缩进，代码注释使用英文。测试用例和平台冒烟验证在本地运行；当前不搭建 CI。提交消息、分支和 PR 等 Git 规则后续决定。
4. **游戏 SDK。** EnTT 留在 Scene 私有实现中。游戏与生成代码只使用 Star 的组件注册、查询、句柄和结构命令。跨模块以 Star 的类型 ID 和类型擦除操作访问组件，不在游戏模块中依赖 EnTT 的模板或类型标识。
5. **编辑数据与热重载。** 编辑器与快照应保留无法识别的类型和字段；Cook 对可达的、无法处理的运行时数据或缺失必需引用报错。注册、启动或恢复失败时，以引擎自有快照重新加载旧模块，恢复未保存内容、选择及撤销/重做记录。第一版不保留运行中的 PIE 状态；若恢复旧模块也失败，保留恢复副本，不覆盖源文件。

## 备选方案与后果

- 不选多生成器、本地三平台加远程 CI 的首期方案：增加单人维护负担。统一构建器减少配置分歧；本地验证仍需要对应操作系统和 GPU，不把未测试等同于通过。
- 不把 EnTT 作为游戏 SDK 的公共依赖：会将底层类型与模块 ABI 和游戏源码耦合。私有实现需要额外的查询适配、类型擦除存储和跨模块测试。
- 不选择静默丢弃未知字段或原地改写活对象：会危及未保存编辑。事务式热重载需要明确模块清理、快照格式和回滚测试；严格 Cook 则要求在打包前修复或迁移可达的异常数据。

## 后续确认

维护者随后确认的分支、提交与推送规则见 [Git 工作规则](../../agent-rules/git.md)。PR、批准与签名规则仍未确定。

## 后果

三正式平台的构建和运行结果必须分别记录，未在对应主机验证的组合不能标记为通过。开发构建与 Profile/Shipping 构建使用不同的模块链接形态，CMake 预设和依赖工具链必须保持可追踪。

游戏 SDK 与 Scene 的私有 ECS 实现隔离，跨模块数据访问需要稳定的 Star 类型 ID 和类型擦除操作。热重载需要引擎拥有的快照、模块清理顺序、任务排空和失败回滚路径，未知编辑数据不能静默丢失。

## 验收边界

- M0 在 Windows x64、Linux x64 和 macOS arm64 分别执行配置、构建、CTest 和窗口示例验证。Linux 的本地结果不能替代另外两个平台。
- M3 验证不包含 EnTT 的外部游戏模块注册、组件访问、卸载和重新注册。
- M5 验证热重载成功迁移、失败回滚、未保存编辑状态、选择、撤销/重做记录和未知字段保留。
- 发布构建验证实际使用固定的 vcpkg baseline 和目标平台 triplet。

## 本地实施记录

- M0 Core 使用 rapidyaml 读取分层 YAML 配置。来源为 `https://github.com/biojppm/rapidyaml.git`，MIT 许可，源码子模块固定为 v0.15.2（`85bfe56e32b1cfe715aa1c39885b1b10761e7482`）。
- c4core 及其 CMake、debugbreak 和 fast_float 依赖由 rapidyaml 上游的子模块提交固定，许可证文件位于各自源码目录。Core 私有静态链接解析器。正式发布的 vcpkg 配置仍按第 2.2.6 节跟进。
