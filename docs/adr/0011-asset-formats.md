# ADR-0011：资产格式

- 状态：已确认
- 日期：2026-11-20
- 关联：[Star Engine 实现方案](../architecture/implementation-plan.md) §2.1、§8、§10；[ADR-0005](0005-reflection.md)

## 背景

编辑器需要可读、可合并和可迁移的源资产。发布运行时需要快速、稳定并适合映射和打包的格式。两种用途对可读性和加载性能的要求不同。

## 备选方案与后果

- 编辑期和发布期都使用 YAML。可调试，但运行时解析成本高，发布包体积和加载时间不可控。
- 全部使用自研二进制。运行时效率高，但源文件难以审阅和合并，版本迁移成本高。
- 编辑期 YAML，发布期反射驱动二进制和 pak。兼顾编辑体验和运行时性能，需要维护 Cook、版本升级和格式兼容。

## 决定

场景、预制体、材质、项目配置和 `.meta` 使用 YAML 文本。烘焙资产和状态快照使用自描述二进制。发布资产放入 pak。格式共享反射类型、字段名、版本和迁移规则。

未知字段、未知组件和未知 GameObject 在编辑期往返保留。Cook 对可达的未知运行时类型、字段、未完成迁移和缺失必需引用报错，不得用空文件覆盖原始数据。

## 后果

序列化器必须区分编辑期保留和发布期严格校验。二进制格式需要版本、字节序、类型标签和失败诊断。资产路径、GUID、类型和字段路径必须出现在 Cook 错误中。

## 验收边界

M1 验证 YAML 与二进制往返、版本升级和未知数据保留。M4/M9 验证导入、Cook、pak 读取和发布包启动。
