# ADR-0005：反射系统

- 状态：已确认
- 日期：2026-11-20
- 关联：[Star Engine 实现方案](../architecture/implementation-plan.md) §2.1、§7；[ADR-0011](0011-asset-formats.md)

## 背景

编辑器、序列化、资产管线和游戏模块需要共享类型、字段、函数和枚举元数据。C++23 没有可用的跨三平台静态反射方案。

## 备选方案与后果

- 手工维护类型注册。实现直接，但重复劳动多，容易与声明不同步。
- 使用宏加模板注册。运行时可控，但复杂类型、字段属性和外部工具集成能力有限。
- 使用 libclang 解析标记并生成代码。构建链路更复杂，但能获得完整 AST 信息和稳定的运行时表。

## 决定

采用基于 libclang 的 StarHeaderTool。通过 `STAR_CLASS`、`STAR_STRUCT`、`STAR_PROPERTY`、`STAR_FUNCTION` 等标记生成类型注册和访问代码。运行时使用 `TypeInfo`、`TypeRegistry` 和类型擦除操作。保留未来迁移到 C++26 静态反射的路径，保持标记语法和运行时 TypeInfo 稳定。

## 后果

生成代码必须进入增量构建依赖图，直接或传递输入变化时重新生成。游戏 SDK 只能依赖生成后的 Star 接口，不依赖 libclang 或生成器内部类型。工具版本和解析参数属于生成缓存键。

## 验收边界

M1 必须从空构建目录完成生成，验证属性、函数、枚举、容器和未知数据的往返。只修改无关实现文件时不得触发重新生成，删除标记或头文件时不得留下旧注册代码。
