# ADR-0001：Gameplay 模型

- 状态：已确认
- 日期：2026-11-20
- 关联：[Star Engine 实现方案](../architecture/implementation-plan.md) §2.1、§9；[ADR-0002](0002-scene-storage-and-hierarchy.md)

## 背景

Star Engine 需要同时支持对象级逻辑和大规模同类数据处理。纯面向对象模型便于编写游戏逻辑，但不适合批量更新。纯 ECS 模型适合数据处理，却会增加对象生命周期、继承和编辑器使用的复杂度。

## 备选方案与后果

- 纯 GameObject 模型。接口直观，但批量系统需要额外的数据组织，缓存局部性和并行扩展较差。
- 纯 ECS 模型。批处理效率高，但对象级生命周期、继承逻辑和编辑器暴露需要额外约定。
- GameObject + ECS。对象负责身份和可选逻辑，组件保存纯数据，系统负责批量处理。需要维护对象和组件之间的生命周期边界。

## 决定

采用可继承的 `GameObject` 加纯数据 ECS 组件的组合模型。GameObject 只保存 GUID、名称、所属场景、生命周期状态和对象句柄。位置、渲染、物理等数据放在组件中。对象级逻辑写在 GameObject 子类中，批量逻辑写在 System 中。

Scene 内部使用 EnTT 作为私有实现。游戏模块和生成代码只依赖 Star SDK 的句柄、组件查询和结构命令接口。

## 后果

对象级逻辑和数据批处理有清晰职责边界。组件访问必须遵循借用生命周期，结构修改必须通过延迟命令缓冲。游戏 SDK 需要提供跨模块稳定的类型 ID、类型擦除操作和查询接口。

## 验收边界

M3 必须验证独立游戏模块不包含 EnTT 头文件即可注册 GameObject 和组件，引擎与游戏能读写同一组件值，阶段边界能提交结构命令，模块卸载后不存在残留函数指针。
