# ADR-0019：M4 阶段渲染器直接使用 Vulkan

- 状态：提议
- 日期：2026-11-28
- 关联：[Star Engine 实现方案](../architecture/implementation-plan.md) §3.1、§11、§12；补充 ADR-0003、ADR-0018

## 背景

M2 交付的 RHI 契约覆盖设备选择、缓冲区与纹理内存、命令提交、屏障工具和渲染图，但管线、采样器、描述符组、栅栏、纹理视图与交换链没有进入 RHI。M4 的前向渲染需要动态渲染、显式屏障、分簇计算和级联阴影，`ForwardRenderer` 因此在实现单元内直接调用 Vulkan（`StarVulkanRuntime` 与 `forward_renderer.cpp`），公共头 `renderer/*.hpp` 仍然不出现 API 类型。

方案 §3.1 要求“渲染器以上的代码不出现任何 API 专用类型”，§11 要求 RHI 覆盖上述对象。当前实现满足前一条，不满足后一条；该偏差没有记录在案，M5 的 ImGui 后端与 M7 的 D3D12/Metal 会直接受其影响。

## 决定

1. 短期允许 `StarRenderer` 的实现单元直接使用 Vulkan，公共头保持 API 无关；RHI 继续负责设备、内存、屏障工具与渲染图。
2. 不以“先补齐全部 RHI 对象”作为 M4 的前置条件。
3. 退出条件：M5 的 ImGui 渲染后端接入前，把图形管线、采样器、描述符组、栅栏、纹理视图与交换链补进 RHI；或者另立 ADR 改为“每后端各有一个 Renderer 实现”。在这条决定落定之前，M7 的 D3D12/Metal 后端不开始。

## 备选方案

- 立即补齐 RHI 并为渲染器重写一层间接：与 M4 的验收目标无关，会推迟标准场景与贴图管线的验证。
- 让公共头暴露 Vulkan 句柄以便编辑器直接取用：把后端类型带进游戏与工具，违背 §3.1 与 §11，且会让 M7 无法推进。
- 维持现状但不记录：后续接手的人会把“渲染器绕过 RHI”误认为既定架构。

## 后果

- 编辑器视口与游戏 UI 的 GPU 交互必须经过补充后的 RHI，否则会重复同一偏差。
- Vulkan 专用代码集中在 `StarRenderer` 与 `StarVulkanRuntime`，替换后端时需要按退出条件收敛。
- 该条目为提议，需维护者确认后才能从方案与附录 C 中引用为既定决策。
